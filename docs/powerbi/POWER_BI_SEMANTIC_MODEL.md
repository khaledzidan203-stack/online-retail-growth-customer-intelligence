# Power BI Semantic Model

## Scope

Checkpoint 6B-1A hardens the existing PBIP semantic metadata only. It does not add business measures, report pages, visuals, SQL objects, or publishing configuration.

## Final Model Inventory

The model contains 10 visible, SQL-backed business tables, one dedicated measure table, and no hidden Auto Date/Time tables:

- `analytics DimDate`
- `analytics DimCustomer`
- `analytics DimProduct`
- `analytics DimCountry`
- `analytics FactTransaction`
- `analytics CustomerRFM`
- `analytics CustomerCohort`
- `analytics CustomerRepeatBehavior`
- `analytics CohortRetention`
- `analytics CohortRevenue`
- `_Measures` (zero-row, relationship-free measure host)

The model contains 50 explicit business measures, all owned by `_Measures`. The report remains one page with zero visuals.

## Dedicated Measure Table

`_Measures` is a zero-row import table created solely to host explicit DAX measures. It has one hidden text column named `Placeholder`, generated by a minimal M `#table` expression, because a table requires a column and partition. It contains no business data and participates in zero relationships.

No explicit measure remains owned by a fact, dimension, RFM, repeat, or cohort table. The 50 measures retain their original expressions and are organized into eight display folders from `01 Core Sales` through `08 Data Quality & Utility`.

## Date Strategy

`analytics DimDate` is the sole date table. Auto Date/Time is disabled through `__PBI_TimeIntelligenceEnabled = 0`; all `DateTableTemplate`, `LocalDateTable`, automatic date relationships, and date-column variation references were removed.

`analytics DimDate` is categorized as `Time`, and `FullDate` is its key date column (`isKey`) with `yyyy-MM-dd` display format. SQL validation confirms 739 distinct, nonblank dates from 2009-12-01 through 2011-12-09 with no gaps.

Sorting is governed as follows:

- `MonthName` sorts by `MonthNumber`.
- `DayName` sorts by `DayOfWeekNumber`.

`DateKey`, `MonthNumber`, and `DayOfWeekNumber` are hidden from report authors but remain available to relationships, sorting, and DAX.

## Relationships

All seven relationships are active, many-to-one, and single-direction from the one-side dimension to the many-side analytical table. There are no bidirectional or many-to-many relationships.

| From table / column | To table / column | Cardinality | Active | Cross-filter |
|---|---|---:|---|---|
| `FactTransaction[DateKey]` | `DimDate[DateKey]` | M:1 | Yes | Single |
| `FactTransaction[CustomerKey]` | `DimCustomer[CustomerKey]` | M:1 | Yes | Single |
| `FactTransaction[ProductKey]` | `DimProduct[ProductKey]` | M:1 | Yes | Single |
| `FactTransaction[CountryKey]` | `DimCountry[CountryKey]` | M:1 | Yes | Single |
| `CustomerRFM[CustomerKey]` | `DimCustomer[CustomerKey]` | M:1 | Yes | Single |
| `CustomerCohort[CustomerKey]` | `DimCustomer[CustomerKey]` | M:1 | Yes | Single |
| `CustomerRepeatBehavior[CustomerKey]` | `DimCustomer[CustomerKey]` | M:1 | Yes | Single |

The three customer summary sources remain physically one row per customer in governed SQL. Their semantic relationships are intentionally modeled M:1 because Power BI one-to-one relationships always filter in both directions; M:1 permits the required single-direction filter flow without changing source grain.

`CohortRetention` and `CohortRevenue` remain disconnected. Their governed grain is `AcquisitionCohort × CohortIndex`, so relating either table directly to customer or transaction-level tables would be unsafe and could create row multiplication or misleading propagation.

## Governed Grains

| Table | Grain |
|---|---|
| `CustomerRFM` | One row per `CustomerKey` |
| `CustomerCohort` | One row per `CustomerKey` |
| `CustomerRepeatBehavior` | One row per `CustomerKey` |
| `CohortRetention` | One row per `AcquisitionCohort × CohortIndex` |
| `CohortRevenue` | One row per `AcquisitionCohort × CohortIndex` |

## Column Visibility

The following 39 technical or governance fields are hidden from the report field list while remaining usable by relationships, sorting, and DAX:

- `DimDate`: `DateKey`, `MonthNumber`, `DayOfWeekNumber`
- `DimCustomer`: `CustomerKey`
- `DimProduct`: `ProductKey`
- `DimCountry`: `CountryKey`
- `FactTransaction`: `TransactionLineKey`, `DateKey`, `CustomerKey`, `ProductKey`, `CountryKey`, `SourceSheet`, `SourceRowNumber`, `DQReviewReason`, `IsKnownCustomer`, `IsCancellationInvoice`, `IsMerchandise`, `IsSalesEligible`, `IsCustomerAnalyticsEligible`, `IsCancellationEligible`, `IsZeroPrice`, `IsNegativePrice`, `IsExactDuplicateAfterFirst`, `IsInExactDuplicateGroup`, `ExactDuplicateGroupSize`
- `CustomerRFM`: `CustomerKey`, `CustomerID`, `RFM_Total`
- `CustomerCohort`: `CustomerKey`, `CustomerID`, `IsLeftBoundaryAffected`
- `CustomerRepeatBehavior`: `CustomerKey`, `CustomerID`
- `CohortRetention`: `IsLeftBoundaryCohort`, `IsPartialObservation`, `ObservationStatus`
- `CohortRevenue`: `IsLeftBoundaryCohort`, `IsPartialObservation`, `ObservationStatus`

## Summarization and Formatting

Default summarization is disabled for identifiers, prices, scores, rates, durations, cohort indices, cohort sizes, active-customer counts, and per-customer metrics. Specifically:

- `DimDate`: `Year`, `Quarter`, `MonthNumber`, `WeekOfYear`, `DayOfMonth`, `DayOfWeekNumber`
- `FactTransaction`: `TransactionLineKey`, `SourceRowNumber`, `Price`, `ExactDuplicateGroupSize`
- `CustomerRFM`: `Recency`, `Frequency`, `Monetary`, `R_Score`, `F_Score`, `M_Score`, `RFM_Total`, `UnitsPurchased`, `ActiveLifespanDays`, `AverageOrderValue`
- `CustomerRepeatBehavior`: `DaysToSecondPurchase`
- `CohortRetention`: `CohortIndex`, `CohortSize`, `ActiveCustomers`, `RetentionRate`
- `CohortRevenue`: `CohortIndex`, `CohortSize`, `RevenuePerOriginalCustomer`, `OrdersPerOriginalCustomer`

Additive facts retain Sum: `FactTransaction[Quantity]`, `FactTransaction[LineAmount]`, `CohortRevenue[Revenue]`, and `CohortRevenue[Orders]`.

Neutral formats were applied: dates as `yyyy-MM-dd`, timestamps as `yyyy-MM-dd HH:mm`, monetary values as `#,##0.00` where appropriate, integer counts as `#,##0`, and retention as `0.00%`. No currency symbol is imposed because the source does not establish a governed reporting currency label.

## Remaining Semantic Considerations

- All explicit measures are centralized in `_Measures`; underlying business tables remain measure-free.
- The three customer analytical tables are unique by `CustomerKey` in SQL, but their model cardinality is deliberately M:1 to enforce safe single-direction propagation.
- Additional business date roles are not connected to `DimDate`; Auto Date/Time will not recreate implicit hierarchies for them.
- Hidden technical fields remain accessible to authored DAX and should not be treated as security controls.
